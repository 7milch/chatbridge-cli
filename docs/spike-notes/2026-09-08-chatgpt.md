# Spike: ChatGPT through the published packages (milestone 4.5)

Date: 2026-09-08. Packages: `@chatbridge/*` 0.2.2, `playwright-core` 1.63.0.
Time-boxed; the throwaway repo `chatbridge-chatgpt` was deleted afterwards.
This note is the only thing kept, plus the issues and skill fixes it names.

## Question

Drive chatgpt.com with the 4.4 skill (`creating-provider-repo`) to expose
what one sample (Rakuten AI) could not: bot / headless detection, a
`contenteditable` composer, lazy login redirects, rate-limit / error banners,
and whether the streaming DOM is appended or replaced.

## Result in one line

`chatgpt -p "Reply with the single word: ping" --headful` returned `ping`
in about 12 s on the unchanged framework; headless is blocked by Cloudflare
and the framework misreports that as an expired auth state.

## Findings

### Bot / headless detection

- Cloudflare serves an interstitial ("Just a moment...") to Playwright's
  headless Chromium, both the headless shell and the new headless mode of
  the full binary, even with a valid saved auth state. Headful Chromium
  passes with no challenge and no CAPTCHA.
- Google sign-in refuses the automated headful browser ("this browser or
  app may not be secure"). Email + password (+ emailed code) works in the
  headful window. Any IdP that fingerprints the browser will do the same.
- Decision (project owner): the framework targets company-internal and
  cooperative chat services. Evading bot protection is out of scope, so no
  stealth plugins, UA spoofing, or attaching to a personal Chrome profile.
  Recorded in `README.md` and `CLAUDE.md`.
- Framework gap: with the challenge page in front, `isLoggedIn` returns
  false and the CLI prints `Auth state for "chatgpt" is no longer valid.
  Run auth login again.` (exit 3). Logging in again would not help; the
  right hint is `--headful`. Filed as a `chatbridge-cli` issue: a provider
  needs a way to say "blocked, not logged out", or the CLI should at least
  mention `--headful` in that message.

### Login

- No lazy redirect. Logged-out and expired states render a guest shell on
  the same origin; login is a modal on that page. Social login hops to
  `auth.openai.com`, so the skill's off-origin rule is still the right
  guard.
- Guests can chat (same trap as Rakuten AI). The logged-in signal is
  `[data-testid="accounts-profile-button"]` present and the guest
  `button[data-mobile-auth-entry-action="login"]` buttons absent.
- The guest shell and the logged-in app are two different DOMs (composer,
  message markup, send button all differ). Discovery must be done in the
  logged-in app; observing the guest page first wastes selectors.
- A hidden `<textarea>` in the logged-in app made a provisional
  `locator(a).or(locator(b)).first().waitFor({ state: "visible" })` time out
  on every poll, so `auth login` never saved. `.or().first()` is only safe
  when every branch matches a visible element.

### Composer

- `#prompt-textarea` is a ProseMirror `contenteditable`. Playwright `fill()`
  works; no synthetic key events needed. The Provider contract needs
  nothing new for `contenteditable`.
- `[data-testid="send-button"]` exists only while the composer is
  non-empty; empty composer shows a dictation control in that slot.

### Generation / completion

- Send button becomes `[data-testid="stop-button"]` within ~400 ms and stays
  until generation ends. Done = stop button gone.
- The send button does not return when done (composer is empty), so the
  skill's default "done = send button visible again" stalls (observed 25 s
  in one run, longer in another). Skill table updated.

### Messages and streaming (input for 3b)

- Turn element: `[data-message-author-role="assistant"]` with a UUID
  `data-message-id`; text in a `.markdown` child whose paragraphs carry
  `data-start` / `data-end` offsets and `data-is-last-node` on the tail.
- Placeholder trap: ~400 ms after send an assistant element with
  `data-message-id="request-…"` and text "…" appears, is removed ~2 s
  later, and only then is the real element inserted. A "count grew" wait
  fires on the placeholder and reads "…". Fix used: wait for the stop
  button to disappear first, then for the count, then the stability read.
- Streaming is appended in place: the same element grows (60 → 182 → 318 →
  408 → 496 → 545 chars at ~400 ms sampling over ~2.5 s). No replacement.
- Rakuten AI also grows one element in place. Both observed services
  append, which lets 3b define streaming capture as "poll or observe the
  newest assistant element's text and emit the delta", with these
  service-specific knobs that belong in the Provider, not the runtime:
  which element is the live one (placeholder swap), what the done signal is
  (stop control gone vs send control back), and an optional tail marker.

### Errors and rate limits

- Not reachable in about six sends; `[role="alert"]` / `[role="status"]`
  stayed empty. Nothing to design against yet; 3b should keep "unknown
  banner" as a timeout, not a parse.

## Skill (4.4) verdict

The procedure held: scaffold → discover → fill → verify worked without
changing the layout, dependency rules, or the method contract. Four trap
rows were added (headless challenge, IdP refusing automation, done signal
via stop control, placeholder element) plus a note that the guest and
logged-in DOMs can differ and that `.or().first()` must not include
possibly-hidden elements.

## Runtime gaps filed

- Challenge page reported as expired auth state (see issue linked from
  milestone issue #22).

## Not done / deferred

- Interactive-mode and gated two-turn E2E were not run: one-shot proved the
  Provider and the streaming question was answered by direct sampling.
- Rate-limit and error banners were not provoked on purpose.
